Tridge design snapshot

One fridge, shared by a household

Tridge will let a Household owner invite other iCloud users into the same fridge. Everyone sees the same inventory and can add, eat, toss, or edit items—even while temporarily offline.

Core architecture settled Final review safeguards included Design only — not implemented
No uninstall The App Store build updates in place and migrates every active legacy item into the first owned Household.
Apple owns membership CloudKit invitations and CKShare handle access. Tridge does not build an account or member system.
Offline-first Each phone saves locally first. iCloud later combines everyone’s operations into the same result.

The design in plain terms

A Household is one shared fridge. Tridge keeps a local copy on each device, while Apple CloudKit carries changes between the Household owner's private database and each member's shared database. The app works with simple snapshots and commands instead of letting screens edit database objects directly.

Milk still behaves like Milk. Adding “Milk” twice produces one visible Milk row whose quantity includes both additions. Internally, Tridge keeps both histories so a late offline update cannot be lost; the user does not see two active Milk rows. A repeat purchase keeps the established art, storage, and expiry unless the user explicitly edits a field in the purchase form.

New modular components

These are the pieces an implementation agent will add. Each has one main job so the feature can be tested in layers.

1. UI and session

What the user sees and which household is active.

HouseholdScreenLists owned and received Households and exposes select, invite, leave, stop, delete, and export actions when allowed.
HouseholdSessionHolds safe value snapshots for the active fridge, capabilities, errors, and sync state.
LaunchStateShows loading, iCloud-required, retry, or one-time migration explanations.

2. Inventory boundary

One controlled doorway between screens and storage.

InventoryCommandsValue requests such as add, edit, eat one, toss one, or clear all.
InventorySnapshotsRead-only household and item values safe for SwiftUI to display.
CoreDataInventoryRepositoryValidates a command, routes it to the correct store, saves atomically, and returns snapshots.

3. Convergence rules

Pure logic that makes different devices reach the same answer.

StockReducerCombines immutable add/eat/toss operations without overwriting another device's change.
ItemGroupReducerProjects permanently linked same-name histories as one logical item with a deterministic canonical metadata member.
InventoryEpochReducerDefines which items survive one or more offline Clear All operations.
DuplicateReconcilerCreates safe exact-name links after local saves and remote imports; it never transfers then deletes history.

4. Persistence and sync

Local replicas plus reliable remote-change processing.

PersistenceControllerLoads one private Core Data store for owned fridges and one shared store for received fridges.
PersistentHistoryProcessorConsumes each imported transaction once, then triggers grouping, snapshots, and reminders.
HistoryTokenStoreRemembers the last processed transaction separately for each store.
StoreScopedSyncMonitorReports only the current account's store activity as up to date, syncing, offline, or needs attention.

5. Sharing and invitations

Thin wrappers around Apple's supported sharing features.

HouseholdSharingServiceCreates/fetches a CKShare and performs Household owner/member lifecycle operations behind a testable protocol.
HouseholdShareItemLets ShareLink send the stable Apple invitation.
ShareInvitationRouterHandles warm/cold callbacks in memory and serializes pending acceptance into the shared store.

6. Account and local effects

Prevents cross-account leakage and keeps reminders correct.

AccountSessionCoordinatorValidates iCloud, opens the correct stores, waits for initial import, and performs safe account transitions.
AccountTaskRegistryTracks account-bound work so old tasks finish or cancel before their stores are removed.
NotificationPlanPurely calculates which expiry reminders should exist for the active fridge.
NotificationServiceApplies that plan and removes alerts belonging to an old account or household.

Three concrete examples

Two people change quantity

Maya has five apples. Alex eats one offline while Maya adds two from a receipt.

5 − 1 + 2 = 6

Each phone may temporarily show its local answer, then both converge to six.

Both people add Milk

Maya and Alex each add one “Milk” while offline and cannot yet see the other row.

1 Milk + 1 Milk = 1 row, qty 2

Two physical histories remain underneath so neither person's addition can disappear.

The iCloud account changes

The app closes the old session, drains its work, removes its local replicas, then opens the new account's replicas.

No cloud data is deleted

The old household disappears only because the new account may not have access. Signing back into the old account reloads it.

Four focused safeguards in the final design

The design keeps all four safeguards inside existing components. None adds a server, a new database model, dependency, or architectural layer.

1

Keep one explicit Stop path

No Manage Sharing in the first rollout

Only Tridge's Stop Sharing action can start copy-before-purge. This removes the system- management race, administrator-role ambiguity, and an extra recovery phase while keeping the owner's locally visible Inventory safe.

2

Keep sharing options minimal

iOS 26 SDK · iOS 18 deployment

Builds use the iOS 26 SDK. ShareLink sets specified recipients and read/write access, while leaving two convenience properties at Apple's documented false defaults because setting them adds no behavior. Newer APIs remain available when they provide real value.

3

Make exact store cleanup finish reliably

Exact three paths only

After Core Data destroys the validated archive, Tridge checks only its exact base, WAL, and SHM paths. It removes a validated remnant and treats “already missing” as success. It never scans the directory or introduces a general cleanup service.

4

Keep invitation state in memory

Manual Household selection after import

Accepted Households enter the picker without changing the active one. Tridge persists no invitation URL, zone hash, phase, or auto-selection intent; a pre-acceptance termination simply requires the member to reopen the invitation.

API references: iOS-compatible participant access options, sharing-option defaults, share invitation acceptance, and Core Data store destruction.

What this architecture does—and does not—add

Included in the first release

  • One Active Household at a time, with owned and received Households listed.
  • The Household owner and accepted members can both edit Inventory.
  • Invite-only Apple sharing with no public or read-only role.
  • Offline local writes and eventual CloudKit convergence.
  • Export, leave, stop sharing, delete, and recovery behavior.
  • An in-place App Store update with automatic active-inventory migration.

Deliberately not added

  • No Tridge login server, member database, or custom member editor.
  • No public links, access requests, member re-invites, or manual merge tool.
  • No Manage Sharing, individual-member removal, or persisted invitation auto-selection.
  • No enforced device lock; the first rollout supports one installation for the Household owner.
  • No promise that every device updates instantly.
  • No migration of eaten/tossed history or legacy receipt text into shared storage.
  • No CRDT or sync package alongside Core Data and CloudKit.
  • No third-party package merely to wrap a few app-specific rules.

Implementation path

The detailed contract already fixes the order. An implementation agent can work through these checkpoints without reopening the product architecture.

Pure rules

Commands, snapshots, stock, grouping, clear, selection, and notification tests.

Core Data stores

Exact model, private/shared stores, launch states, capabilities, and active-inventory migration.

Repository migration

Move every inventory path from SwiftData objects to snapshots and commands.

History and accounts

Remote imports, sync state, account isolation, grouping, reminders, and bootstrap.

Sharing UI

Household picker, invitation sending, and in-memory cold/warm acceptance.

Lifecycle and rights

Leave, stop, delete, export, recovery, and failure handling.

Repository verification

Linux tests, macOS build/tests, CI, docs, and release handoff.

Live acceptance

Two iCloud accounts, development schema, TestFlight update, then schema promotion.
