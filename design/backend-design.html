How a request is protected — the gauntlet, in code order

429
Per-IP rate limit — 20 req/minWorkers rate-limiting binding, keyed by CF-Connecting-IP. The outermost layer on every route — the unauthenticated attest endpoints (KV writes + X.509/ECDSA work) are throttled too, and credentials can't be brute-forced faster than 20 tries/min. Retry-After: 60.
404·405
Route + methodPOST only; /v1/receipt-scan plus the attest endpoints when App Attest is configured.
415·413·400
Strict input validationimage/jpeg only; 8 MB cap enforced via Content-Length before buffering, re-checked after; empty bodies rejected.
401
Client auth — App Attest (prod) or bearer token (test)Prod: per-scan App Attest assertion over the image bytes + strictly-increasing sign counter (verified with node-app-attest; device key + counter in DEVICE_KV). Test: static SCAN_API_TOKEN, SHA-256 digests + timingSafeEqual. Registration: POST /v1/attest/challenge → POST /v1/attest. Auth binds to the buffered image, so it runs just after validation, before any billable work.
429
Per-device daily quotaKV counter keyed by the attested device (10 scans/day), on top of the per-IP limit.
200
Proxy the scanbase64 → Responses API with strict schema; refusal/unparseable retried once then 422; upstream errors → 502 with the OpenAI body logged, never echoed.

Plus: structured JSON logs (Workers Logs, observability on, full sampling) that never contain image bytes or key material; max_output_tokens: 4000 bounds each scan's spend; the README mandates a dedicated OpenAI test-project key with a budget cap, so a leaked token's worst case is a capped test budget.

API contract (implemented)

POST /v1/receipt-scan
X-Attest-Key-Id: <keyId>                      # App Attest (prod + on-device test builds)
X-Attest-Assertion: <base64>                  # assertion over the image bytes
  # — or, for the local smoke harness only —
Authorization: Bearer <SCAN_API_TOKEN>      # test env worker secret
Content-Type: image/jpeg                     # raw body, ≤ 8 MB

200 OK  application/json                     # exactly what the app parses today
{ "items": [ { "id": "milk", "name": "Whole Milk",
    "receipt_text": "WHL MLK", "quantity": 1, "shelf_life_days": 7 } ] }

400 empty body                413 body > 8 MB
401 bad auth / unregistered   415 not image/jpeg
404/405 wrong route/method    422 unparseable receipt or refusal (after 1 retry)
429 IP rate limit or device quota (Retry-After)   502 OpenAI failure (body never echoed)

# App Attest registration (once per install):
POST /v1/attest/challenge  → { "challenge": "<base64>" }
POST /v1/attest            { keyId, attestation, challenge }  → { "ok": true }

All errors are {"error": "<human-readable message>"}. The 200 body is passed through from the schema-constrained model reply, so the app's existing parser (defaults, clamps, unknown-id fallback) keeps working unchanged.

The worker already runs the production posture, so the prod split is purely additive — a new env.prod block, its own KV + OpenAI key, and a build-config URL in the app. Deferred by choice: one consistent worker is simpler pre-launch. See server/README.md → Adding a production worker later.

Cloudflare best practices applied

Built against the workers-best-practices skill from Cloudflare's official cloudflare/skills plugin:

  • Current compatibility_date + nodejs_compat; JSONC config.
  • Env generated by wrangler types — bindings are never hand-written; only the two secrets merge in via secrets.d.ts (they can't appear in config by design).
  • Secrets exclusively via wrangler secret put — nothing in repo or CI config, consistent with the repo's existing key ban.
  • Observability enabled (full head sampling) with structured JSON logs.
  • No floating promises, no module-level request state, explicit try/catch (no passThroughOnException), Web Crypto only, timing-safe secret comparison.

Migration plan — where we are

  1. Stand up the Worker (test env) — deployed & verified, PR #15

    Live at tridge-scan-api-test.forrestzjb.workers.dev with both secrets set and the fixture-receipt scan passing end-to-end. Ongoing deploys: connect the repo to Workers Builds (dashboard → worker → Settings → Builds; root directory server, branch main, watch paths server/**) — the one remaining dashboard step. CI gates PRs with the server suite.

  2. App switched to ProxyLLMService; BYOK removed

    Done in one step rather than staged. ScanFlowModel now builds a ProxyLLMService (via ScanAPIConfig) as its only scan path. Deleted: the Settings key field, KeychainStore, the direct-OpenAI client, the app-side prompt/schema copies, and the parity test — the contract lives only server-side. The app authenticates with the SCAN_API_TOKEN bearer token, bundled at build time as the gitignored resource Tridge/Resources/ScanAPIToken.txt (a custom Info.plist key is silently dropped by Xcode's generated plist), never committed. The receipt smoke test drives the live worker through ProxyLLMService (token from env/.env, BACKEND_URL to retarget). See the decision log → 2026-07-07 — App scans through the worker.

  3. Production-grade auth (App Attest) on one worker — implemented, PR #21

    Apple App Attest verification (attestation registration + per-scan assertion, via node-app-attest), per-device quotas, and store:false. Device keys, sign counters, and quota counts live in the DEVICE_KV namespace. The app (AppAttestAuthorizer) signs each scan and ships no static token; the worker keeps a bearer token only for the local smoke harness. One worker (tridge-scan-api-test) serves every build via a single ScanAPIConfig.baseURL. Server suite and swift test green. See wiki/decisions.md → 2026-07-10.

    Owner-only to go live (no code): create the DEVICE_KV namespace and paste its id into wrangler.jsonc; set secrets (OPENAI_API_KEY, APPLE_TEAM_ID, SCAN_API_TOKEN); connect Workers Builds; verify a TestFlight build scans end-to-end. See server/README.md → Deploy.

To deploy the test env now: add the CLOUDFLARE_API_TOKEN + CLOUDFLARE_ACCOUNT_ID repo secrets (CI deploys on merge), or run the three commands in server/README.md → Deploy locally. Remember: the OpenAI usage is now billed to us — set a budget cap on the test project.
