Tridge

Scan a grocery receipt, and your fridge appears on screen — every item as a prebuilt image floating on a soft background, quietly turning amber, then red, as it nears expiry. This document is the complete visual/product build spec: design direction, every screen and interaction, data model, LLM contract, dev-environment requirements, and acceptance criteria.

Sharing-release contract: the persistence, collaboration, account isolation, Household screen, no-uninstall active-inventory migration, lifecycle, privacy, implementation order, and two-account verification details are normative in wiki/household-sharing.md. The summaries below agree with that contract; if an implementation detail is not visual, use the wiki page.

Design direction

Minimal like a product shelf, playful like a game inventory

The reference is skylrk.com: a near-empty page where the product images are the interface — generous whitespace, no cards, no chrome, image-first. The home screen borrows that stance exactly: a soft ambient background and the item images floating directly on it. No tiles, no cards, no list chrome, no tab bar — a single scan button at the bottom.

Item art is a prebuilt image per item. For v1 the prebuilt set is the system food emoji rendered large (they are high-quality, cover ~120 foods, and cost nothing); the code treats art as a lookup — every item carries an id from the curated ItemID vocabulary (specific foods plus generic buckets and unknown), and Artwork maps id → emoji — so a custom illustrated sprite set can replace emoji later by dropping PNGs into the asset catalog keyed by the same ids. The game-inventory feel comes from the layout and badges, not from slot frames: fixed grid cells, a stack-count badge ("×12"), and a status pill riding the item's shoulder.

Background, not surface

A soft cool gradient (chilled-air feel) with a faint top glow — like light inside a fridge. Items cast a soft drop shadow so they sit "in" the space.

Items are the UI

Only images, names, and pills. Header is one word ("Fridge"), an item count, and a small gear for Settings. One hero action: the green scan button.

State reads at a glance

Freshness is encoded twice — the pill's color and its label ("12d", "Today", "✕ 1d"). Expired items desaturate.

Native iOS feel

SF Pro (Rounded for display), standard sheets, haptics on every consume action. No custom nav paradigms.

＋ Household screenLists owned and received households, with a checkmark on the locally active one. Owners can rename, send an invite with ShareLink, stop sharing while keeping a private copy, export JSON, or delete owned cloud data. Household members can export visible data or leave. Invite-only/read-write sharing, account/error/sync states, destructive confirmations, migration behavior, and exact lifecycle copy are normative in the household-sharing architecture.

The core loop

Shop, then scan

User taps the scan button, photographs the receipt. VisionKit auto-crops and de-skews.

LLM parses everything at once

One API call returns a curated item id, clean name, quantity, and shelf-life estimate per item. No barcode DB, no OCR post-processing.

Confirm in one tap

Review sheet fixes trust: user corrects anything odd, then "Add N items". Dates the user edits are marked userSet and never overwritten.

Live inventory

Home grid shows everything, soonest-expiring first. Pills tick down daily; notifications fire at T−2 days and on expiry day at the configured hour.

Eat or toss

Drag an item to a drop zone (or use the detail sheet buttons). Consumed items leave the grid but persist, so waste stats can be added later.

Data model

Core Data + CloudKit sharing schema

EntityPurposeKey fields
HouseholdRecordOne owned or received fridge and the logical aggregate shared in one Core Data record zone.UUID, model version, name, initial inventory epoch, created/modified dates, inverse item, merge-claim, and clear-event relationships
FridgeItemRecordDurable item metadata and stock-history anchor in exactly one household/store/share.UUID, model version, immutable name + normalized name, canonical causal-epoch context, art key, storage, timezone-independent Purchase/Expiry Day ordinals, expiry source, timestamps, inverse household/stock relationships
StockChangeRecordImmutable, idempotent stock or explicit-delete event; authoritative for quantity and consumption. Clear All is represented only by the Household causal frontier.UUID command id, model version, signed delta, reason, occurrence date, inverse item relationship
ItemMergeRecordImmutable, permanent claim joining concurrently created exact-name active items into one lossless logical item.UUID, model version, sorted endpoint UUIDs, creation date, inverse household relationship
HouseholdClearRecordImmutable edge in the causal inventory-epoch graph, so Clear All covers unseen earlier items without discarding additions made after a concurrent clear.UUID, model version, epoch UUID, canonical parent-frontier UUIDs, Lamport revision, occurrence date, inverse household relationship

Every confirmed purchase creates a hidden physical root stamped with the household's current causal inventory frontier. A logical item is the connected component of permanent merge claims among current roots. Quantity is max(0, sum(unique stock-event deltas across every member)); immutable deleted events and household clear epochs prevent deleted or superseded history from returning. Thus two offline users adding one active “Milk” converge to one visible Milk with quantity two without deleting either history. Saved names are read-only, so a link never needs to split; a correction means deleting and adding the item again. The lowest-id member supplies the logical item's metadata, and later metadata edits target it. A zero projection is hidden but may revive when a delayed valid operation arrives; a new purchase always gets a fresh root. Clear All writes no item-level event. Two concurrent Clear All commands create coexisting frontier branches, so groceries added after either clear survive; a later clear that has imported both branches supersedes both. Urgency is computed from the canonical Expiry Day, and Food Category remains computed from artKey. Raw receipt text stays only in the in-memory review draft and is not persisted or shared. The exact fields, optionality, inverses, delete rules, encrypted attributes, private/shared store routing, conflict semantics, and account isolation are normative in household-sharing.md. It supersedes the shipping SwiftData runtime schema. The first sharing build automatically migrates every active legacy item into the user's first owned Household; eaten/tossed rows and old receipt text remain only in the retained local archive.

LLM integration

One vision call does receipt → inventory

Tridge's Cloudflare Worker calls the OpenAI Responses API with model gpt-5-mini (fast, pennies per receipt); the app never carries an OpenAI key. The response shape is enforced server-side with a strict Structured Outputs JSON Schema, so replies always match the contract; the prompt carries only the content rules. Per item the LLM returns exactly: id (one of the curated ItemID vocabulary — the schema's enum makes anything else impossible), name, receipt_text, quantity, shelf_life_days, storage (fridge, freezer, or pantry — where the purchase belongs at home, editable via the review sheet, Item Detail, or manual add). No store name, no purchase date (the app stamps the scan day), no emoji (art is resolved from id on-device), and no food category (derived on-device from id — see the data model). Unknown-item strategy is tiered: specific id → generic bucket id (fruit, vegetable, meat, …) → unknown, which the review sheet flags amber for fixing; ids added to the vocabulary later decode as unknown on older builds.

POST https://api.openai.com/v1/responses
headers: Authorization: Bearer <key> · content-type: application/json
body: { "model": "gpt-5-mini", "max_output_tokens": 4000, "reasoning": { "effort": "low" },
        "store": false,          ← disables Responses application-state storage for receipt scans
        "text": { "format": { "type": "json_schema",
                  "name": "parsed_receipt", "strict": true, "schema": SCHEMA }},
        "input": [{ "role": "user", "content": [
          { "type": "input_image", "image_url": "data:image/jpeg;base64,<receipt>" },
          { "type": "input_text", "text": PROMPT }]}] }

PROMPT (verbatim — content rules only; the JSON shape and allowed id values come from SCHEMA):

This is a grocery store receipt. Extract every FOOD and BEVERAGE item.
Rules:
- Expand abbreviations into clean, human-friendly names ("WHL MLK 1GAL" → "Whole Milk").
- "name" is the bare food name and nothing else — strip weights, sizes, counts,
  prices, packaging, and brand or marketing words ("Jalapeño Pepper (0.34 lb)" →
  "Jalapeño Pepper", "Local Eggs (dozen) — 6 dozens" → "Eggs").
- Skip non-food lines: tax, totals, coupons, bags, household goods, loyalty points.
- If one line has a quantity multiplier, set quantity accordingly.
- For "storage", say where the item belongs once home: "freezer" for items
  sold frozen or normally kept frozen, "pantry" for shelf-stable goods kept at
  room temperature (canned goods, dry pasta and rice, chips and crackers,
  unopened condiments), "fridge" for everything else.
- Estimate each item's typical shelf life in days from purchase, assuming it
  is stored appropriately at home (refrigerated promptly where applicable).
- For "id", pick the closest match from the allowed values. Prefer a specific
  id; if nothing specific fits, pick a generic one (fruit, vegetable, dairy,
  meat, seafood, bakery, beverage, grain, snack, condiment, frozen).
- If a line is probably food but you cannot tell what it is, use id "unknown"
  and name "Unknown item".
  • Parsing: structured outputs guarantees schema-valid JSON, but the client stays defensive: strip Markdown code fences if present, then JSONDecoder. The Worker owns the one automatic malformed-response retry; the client never repeats the Worker request automatically and surfaces its retry alert if the final response still cannot decode.
  • Image prep: longest edge ≤ 1568px, JPEG quality 0.8, before base64.
  • Unidentifiable items come back as id unknown and get the amber "tap to fix" treatment in the review sheet, never silently dropped.
  • Client authentication: the app carries no OpenAI key or static Worker token. Apple App Attest authorizes device scans; "Type to add" remains entirely local.

Development environment

What you need to build and run this

The short version: a native iOS app cannot be compiled on a Linux VPS. Swift itself runs on Linux, but the iOS SDK, SwiftUI, the simulator, and code signing exist only inside Xcode on macOS — Apple ships them nowhere else. So the question is where the macOS machine lives:

OptionWhat it looks likeCost / trade-off
A · Your own MacXcode 26+ on any Apple-silicon Mac (a base Mac mini is enough). Builds use the iOS 26 SDK while the app supports iOS 18+. Full simulator, instant iteration, deploy to your iPhone over cable or Wi-Fi.Best experience. Mac mini from ~$599 if you don't own one.
B · Rented cloud MacA macOS VM you remote into: MacStadium, Scaleway Apple silicon, AWS EC2 Mac. Run Xcode over screen sharing; your Linux VPS workflow stays for everything else.~$0.10–0.65/hr or ~$50–130/mo; AWS has a 24h minimum. Remote-desktop Xcode is usable but laggy.
C · Linux VPS + macOS CIYou (and Claude Code) write all the Swift on the VPS. GitHub Actions macOS runners compile, run the unit tests, and upload builds to TestFlight. You never touch a Mac directly.Free for public repos (macOS runners bill 10× minutes on private free tier). Iteration loop is 10–20 min per build and there's no simulator screenshot loop — fine for an agent one-shot + fix cycles, painful for pixel-level UI tweaking. Requires the $99/yr Apple Developer Program for TestFlight signing.
Realistic recommendation for your setup: write the code on the VPS, build with option C, and if the UI needs more than a couple of correction rounds, spin up a cloud Mac for a day (option B) to polish with the simulator. Swift Package structure + unit tests (parsing, urgency logic) are Linux-runnable, so most logic bugs get caught before a macOS build is ever needed.

Definition of done

Acceptance criteria for the one-shot build

  • App builds clean in Xcode for iOS 18 simulator; every third-party dependency is justified, license-reviewed, exactly pinned, locked, attributed, and isolated behind a replacement boundary where practical.
  • Scanning a real Trader Joe's–style receipt yields a review sheet with ≥90% of food lines as clean names, each with art, quantity, and a plausible future expiry date.
  • Confirming the sheet adds items to Home, sorted soonest-first, with staggered pop-in animation.
  • Items render with no background frame — art + shadow directly on the gradient; pills green ≥3d, amber 1–2d, red today/expired; expired art desaturates; app badge equals expired count.
  • Home has exactly one control at the bottom: the circular scan button. No tab bar.
  • The header's filter glyph opens the Filter sheet (Storage + Food Category chip groups); selections filter the grid live, tint the glyph green with a dot, show as removable tags under the header, and drive the header count. A no-match filter shows the "Nothing matches" ghost; an empty fridge shows no filter UI and clears any active filter.
  • Scanned items land in the LLM's storage guess (fridge, freezer, or pantry); review rows show a display-only Food Category chip and an editable Storage chip; every item's Food Category derives from its art's ItemID.
  • Long-press-dragging an item dims the grid and reveals the two drop zones; dropping on "Ate it"/"Tossed" fires a haptic and updates status; ×N quantity decrements before removal; releasing elsewhere cancels.
  • Editing a date in Item Detail sets expirySource = userSet, reschedules both notifications, and survives relaunch.
  • Notifications fire at T−2d and expiry day at the configured hour (verifiable with a short-dated test item).
  • The app carries no API key; App Attest/auth failure and network failure show a safe retry message; malformed LLM JSON gets one automatic Worker-side retry.
  • An installed TestFlight/App Store build updates without uninstalling, migrates every active legacy item exactly once into its first owned Household, preserves preferences and App Attest, and removes old expiry reminders even while iCloud is signed out. Migration waits for account validation and its explanation repeats until acknowledged. Automatic upgrade retains eaten/tossed rows and old receipt text only in the legacy SwiftData archive, while explicit old-local-inventory erasure destroys only that archive and sidecars.
  • An owner can invite a second iCloud account; both peers can view/add/edit/eat/toss offline and converge through immutable stock events without a lost scalar increment. Warm and cold acceptance both work, then the member selects the imported Household from the picker. Every purchase gets a fresh causal root; exact-name active roots—including items on two concurrent-clear branches—become one logical row with summed quantity through permanent immutable merge claims, and no physical history is deleted. Every saved name is read-only, while quantity, art, storage, and expiry remain editable. The lowest-id physical member supplies metadata; a same-name purchase preserves those values except for fields the user explicitly edits, and ordinary property-level conflict handling is accepted for concurrent edits.
  • Clear All writes only a deterministic causal Household frontier—no item-level clear events—so a previously unseen item from a superseded context cannot reappear. Concurrent clears retain groceries added after either branch; a later clear that has imported both branches supersedes both.
  • The Household screen can switch among personal/received fridges, manually select an accepted Household, export every physical/history/epoch record in versioned JSON, leave or handle lost access safely, refresh invitation titles after rename, stop sharing while preserving the owner's locally visible active stock after warning about unseen offline edits, and delete owned CloudKit data. An unshared private deletion reports completion only after every captured CloudKit record is confirmed absent.
  • No/restricted iCloud account never exposes cached inventory; account changes invalidate and drain every old-generation task—including an incomplete two-store load—before removing stores or activating the next account, then rebuild account-scoped stores/tokens/selection before showing data. Setup/import events emitted during loading are buffered for the correct stores, and a completion from the prior account's store session cannot affect the new sync status. A fresh empty cache waits for successful private import before creating My Fridge. Public/read-only/member-reinvite options are unavailable in ShareLink; Manage Sharing and individual-member removal are absent. Old-scope pending/delivered notifications are removed.
  • Empty fridge shows the empty state; dark mode renders per the dark tokens; Reduce Motion disables the pop-in spring and drag float.
  • Unit tests pass on Linux via swift test where possible: receipt parsing, urgency, stock reduction/idempotency, household selection, and notification diffing; Apple-platform persistence tests and the two-account acceptance matrix in household-sharing.md also pass.
Sharing-release build order for the agent: pure stock/selection/notification contracts + Linux tests → exact Core Data model and account-scoped private/shared stack → repository-backed migration of every view and scan confirmation → persistent history + notification reconciliation → Household UI and invitation bridge → leave/access-loss/stop/delete/export lifecycle → full Gate and CI → authorized two-account development acceptance → production schema promotion and TestFlight upgrade acceptance. Exact checkpoints and the external release handoff are in household-sharing.md.
