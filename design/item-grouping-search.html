1Problem & goals

Both save paths insert unconditionally. ScanFlowModel.confirm (Tridge/Views/Scan/ScanFlowModel.swift:150–176) maps every review row into a fresh FridgeItem and calls context.insert; ManualAddSheet.add (ManualAddSheet.swift:81–98) does the same. Nothing ever queries the existing active inventory, so a double-scan or a re-purchase shows two "Milk" sprites on the home grid. There is also no name normalization anywhere, and LLM names vary between runs ("Jalapeño Pepper" vs "Jalapeño Peppers").

Four user-facing outcomes, sharing one foundation (a canonical name key):

  1. No duplicates — scanning the same receipt twice, or re-buying an item, quietly bumps the existing entry's quantity instead of creating a twin (#26).
  2. Lookup — find an item in the inventory by typing part of its name.
  3. Quick add — while typing a name in manual add, matching existing/past items appear; one tap adds (+1 an item already in the fridge, or re-add a past item with everything prefilled).
  4. Minimal input — manual add needs only a name: art is inferred automatically and consistently from it, everything else defaults.

Non-goals: fuzzy auto-merging ("2% Milk" ≠ "Whole Milk" — §2), barcode identity, units/measures (quantity stays an integer count 1–99), per-batch expiry tracking (skipped with the old Option C), and any server involvement — all of this is on-device.

2What others do (research)

App / sourcePatternTake-away for Tridge
AnyList Silently auto-combines same-named list items and sums quantities. Autocompletes from your own past items; tapping a suggestion re-adds it with remembered details. Closest to the chosen design — silent grouping plus suggestion-with-remembered-details quick-add.
Grocy Splits product from per-purchase stock entries, each with its own best-before date; consumes first-expiring-first-out. The fully general model. Skipped for now (owner call), but the stored name key below is exactly its future product key, so the door stays open.
Plan to Eat (postmortem) Moved away from silent pantry automation because users couldn't tell why things changed. The risk to manage in a silent merge: mitigated here because the review page is still an explicit confirmation step, and merging only ever adds quantity — it never deletes or reschedules anything.
Expensify / Zoho / Klippa Duplicate-receipt detection fingerprints parsed content, never image pixels. Kept as a possible future guard; not in scope now (no banners, per owner).

Platform findings that shaped the design:

  • Comparison: .lowercased() equality is a documented anti-pattern (Turkish I, ß). Use String.folding(options: [.caseInsensitive, .diacriticInsensitive], locale:) to precompute a stored canonical key.
  • Merging: exact-normalized-match only. A false merge (silently absorbing a distinct item) is worse than a duplicate; fuzzy signals belong only where a human confirms (suggestions).
  • Search scale: tens-to-hundreds of rows — a full in-memory scan of short strings is sub-millisecond, so no FTS or trigram machinery. With the floor now at iOS 18, the stored key also gets a real SQLite index for free: #Index<FridgeItem>([\.normalizedName]).
  • Autocomplete ranking (industry consensus): exact > whole-string prefix > word-boundary prefix ("mi" → "Whole Milk") > substring; tie-break by recency/frequency. No debounce needed for a local dataset this small.

3Foundation: identity & auto art

Three pure-logic pieces, all in Tridge/Core/ so they compile into the FridgeCore package and run under swift test on Linux (FridgeItem itself is not in the package, so all of them operate on plain values).

3.1 The canonical name key

// Tridge/Core/NameKey.swift  (FridgeCore — Linux-testable)
enum NameKey {
    /// Canonical form used for identity and search: case- and
    /// diacritic-folded, trimmed, inner whitespace collapsed.
    /// "  Jalapeño  Pepper " → "jalapeno pepper"
    static func normalize(_ name: String) -> String {
        name.folding(options: [.caseInsensitive, .diacriticInsensitive],
                     locale: .current)
            .split(whereSeparator: \.isWhitespace)
            .joined(separator: " ")
    }
}

The key is persisted as a new indexed normalizedName property on FridgeItem (§7) rather than recomputed per comparison. Deliberately excluded: plural folding (naive "-s" stripping breaks "Grapes", "Hummus") — #25's bare-name prompt rule already reduces plural variance, and a residual "Pepper" vs "Peppers" pair is a visible, user-fixable miss rather than a silent wrong merge.

3.2 The matching key: the name, alone

Two rows are "the same item" iff their normalized names are equal. Per owner review, storage is not part of the key — one name means one thing in a household, and it simplifies the design: the planner drops a parameter, and a merge simply keeps the existing item where it already lives (a rescanned "Milk" tops up the fridge Milk regardless of the current storage default). The one behavior to know about: the same name split across fridge and freezer on purpose ("Bread" in both) will always group; the natural escape is naming them apart ("Frozen bread"), which matches how people actually label things. artKey also stays out of identity — with art now derived from the name (§3.3), it carries no independent signal.

3.3 Automatic, consistent art — ArtInference

Manual add currently makes the user hand-pick art from the ItemID grid. That input is removed: art resolves automatically, through a tiered lookup where the household's own history always outranks the rules —

TierRuleExample
0 · RememberedThis normalizedName was saved before → reuse its artKey (latest row wins). The user's own pick outranks every rule below, forever.you once set "Mooncake" → 🥮; every future Mooncake is 🥮
1 · ExactName equals a vocabulary display name or rawValue."milk", "ice cream", "green onion"
2 · SynonymSmall curated table."scallion" → greenOnion, "yoghurt" → yogurt
3 · TokenA word of the name hits 1–2; last matching token wins (head-noun heuristic)."chocolate milk" → milk
4 · TypoEdit distance ≤ 1 per token against 1–3 — safe here because art is cosmetic and previewed live before saving (a wrong guess is visible, not silent)."bannana" → banana
5 · Unknown🛒 — and the art slot itself becomes the invitation to fix it (below)."Leftover curry base"
// Tridge/Core/ArtInference.swift  (FridgeCore — Linux-testable)
enum ArtInference {
    /// Tiers 1–5 for names never seen before: exact → synonym →
    /// token → typo(≤1/token) → .unknown. Pure function of the
    /// normalized name — no randomness, no context.
    static func itemID(for name: String) -> ItemID
}
// Tier 0 (remembered art) is a history lookup by normalizedName,
// done by the caller — no new schema: the memory IS the saved rows.

The no-match flow. When resolution bottoms out at 🛒, the live art slot next to the name field shows the 🛒 with a dashed ring — the design's single, quiet "this needs you" affordance. Tapping it opens the existing ArtPicker; the choice saves with the item and, via tier 0, is remembered for every future add of that name. Ignoring it is also fine: the item saves as 🛒, honest and findable by name, fixable any time in the detail sheet (which also updates the remembered art). This is what keeps the design scalable and minimalist: zero prompts when inference works, exactly one optional tap when it doesn't, and the household's vocabulary grows organically without the curated ItemID enum ever needing to.

  • Scan path: unchanged — the LLM already returns a schema-enforced ItemID, which stays authoritative for scanned rows.
  • Manual add: the ArtPicker row disappears; the resolved emoji fills the sheet's hero art live as the user types (animated in §6). Suggestion chips carry their remembered artKey — tier 0 by construction.
  • Consistency guarantee: same name → same art, always: tier 0 makes the user's correction sticky; tiers 1–5 are a pure function of the name. Changing art never affects identity.

5Merge rules — spec

// Tridge/Core/MergePlanner.swift  (FridgeCore — Linux-testable)

/// Value snapshot of an active inventory row (FridgeItem is not in
/// the package, so the planner never touches the @Model type).
struct MergeCandidate: Sendable {
    let id: UUID
    let normalizedName: String
    let quantity: Int
    let isExpired: Bool
    let purchaseDate: Date
}

enum MergeDecision: Equatable, Sendable {
    case insert
    case merge(into: UUID, resultingQuantity: Int)
}

enum MergePlanner {
    /// Exact normalized-name match against active items; expired
    /// items never absorb a new purchase (a fresh buy is a new
    /// batch). Ties → most recent purchase.
    static func decide(name: String, quantity: Int,
                       existing: [MergeCandidate]) -> MergeDecision {
        let key = NameKey.normalize(name)
        guard !key.isEmpty,
              let match = existing
                  .filter({ $0.normalizedName == key && !$0.isExpired })
                  .max(by: { $0.purchaseDate < $1.purchaseDate })
        else { return .insert }
        return .merge(into: match.id,
                      resultingQuantity: min(match.quantity + quantity, 99))
    }
}

Behavioral rules, in order:

  1. Candidates: active items only (statusRaw == "active"). Consumed history never absorbs new purchases.
  2. Eligibility: expired items are skipped — a new purchase of something already past its date is a fresh batch and inserts as its own row. This is also what keeps "old expiry wins" from ever hiding fresh food behind a red sprite. The threshold is deliberately just isExpired, not "near expiry": near-expiry matches are exactly the double-scan case we do want to group.
  3. On merge: existing.quantity = resultingQuantity; expiryDate/expirySource untouched (#26's settled decision — user-set dates are never overwritten); storage untouched (the item stays where it lives); receiptText refreshed to the newer line; notifications left as scheduled (expiry didn't change, and NotificationService.schedule is idempotent if re-run).
  4. Within one receipt: rows that match each other (the LLM emitted "Milk" twice) coalesce into one review row at parse time, quantities summed — the planner then sees one row per name.
  5. Both paths: ScanFlowModel.confirm runs the planner per row at save; ManualAddSheet runs it once when Add is tapped. One manual-add nuance: because the edit page shows an expiry field (prefilled from the existing item when a chip was used), a merge applies the expiry only if the user changed it from the prefill — then it's a deliberate edit and saves as .userSet. Untouched, the existing item's date and source stay exactly as they are. The invariant holds: only an explicit user action can overwrite a date, never a default or a guess.

6Search & quick-add suggestions

Both features are read-side consumers of the same stored key and one shared ranking helper:

// Tridge/Core/NameSearch.swift  (FridgeCore — Linux-testable)

struct SearchEntry: Sendable {
    let normalizedName: String
    let lastUsed: Date      // most recent purchaseDate
    let useCount: Int       // times this name was added
}

enum NameSearch {
    /// Rank: exact > whole-string prefix > word-boundary prefix
    /// ("mi" → "whole milk") > substring; ties by lastUsed,
    /// then useCount. Query is normalized with NameKey first.
    static func rank(query: String, in entries: [SearchEntry],
                     limit: Int) -> [SearchEntry]
}

All matching happens on normalizedName, so "jala" finds "Jalapeño Peppers". At this scale ranking runs in memory per keystroke with no debounce; the #Index on the column (§7) keeps the backing fetches cheap as history grows.

6.1 Manual add: one edit page, chips for quick fill

One page serves every case — brand-new item or re-add — so there is never a fork in the flow (owner call). The page is the familiar editor (name · quantity · expiry · Add), with a single addition: a row of suggestion chips sitting directly above the name input box. Before typing, the chips show the most recently/frequently added items; typing re-ranks them through NameSearch. Tapping a chip fills the form — it never commits anything: name and art fill in, and expiry prefills with the existing item's current date (in-fridge chip) or today + that item's typical shelf life (past-item chip). Quantity always means "how many I'm adding" and defaults to 1. Everything stays editable after a fill; the single Add button confirms. The hero art atop the page is its one silent control: it fills itself (§3.3), invites a tap only when resolution lands on 🛒, and a tap there opens the picker without adding any standing chrome. The name row itself is a standard label-left / input-right form row, matching Quantity and Expires.

6.3 Where suggestions come from

Derived from history, no new entities: group all FridgeItem rows (any status — consumed rows stay in the store forever) by normalizedName at sheet-open; the latest row wins for art and storage, medians give the typical shelf life. For years of solo use (~1–2k rows) this is milliseconds. A dedicated catalog entity was considered and rejected: it's a denormalized cache to keep correct on every insert/merge/rename — the classic drift-bug surface — and its real payoff only arrives with the (skipped) product/batch model.

7Data schema & migration

FridgeItem after this change — one added property, one added index, everything else untouched:

@Model
final class FridgeItem {
    #Index<FridgeItem>([\.normalizedName])   // iOS 18 floor (owner call)

    var id: UUID = UUID()
    var name: String = ""
    var normalizedName: String = ""   // NEW — NameKey.normalize(name)
    var receiptText: String?
    var artKey: String = ItemID.unknown.rawValue
    var quantity: Int = 1
    var storageRaw: String = StorageLocation.fridge.rawValue
    var purchaseDate: Date = Date()
    var expiryDate: Date = Date()
    var expirySourceRaw: String = ExpirySource.llmEstimate.rawValue
    var statusRaw: String = ItemStatus.active.rawValue
    var consumedDate: Date?
    // computed accessors unchanged
}

normalizedNamenew, indexed, default ""The identity + search key. Default keeps the schema CloudKit-compatible (repo invariant).
nameunchangedDisplay form. Every write goes through a setName(_:) helper that updates the pair atomically.
artKeyunchanged type; now auto-assigned on manual add via ArtInferenceCosmetic only — never part of identity.
quantityunchangedMerge adds into it, clamped 1…99.
storageRawunchangedNot in the matching key (owner call); a merge keeps the existing item's storage.
expiryDate / expirySourceRawunchangedNever modified by a merge (#26's settled decision).
statusRaw, purchaseDate, consumedDate, receiptText, idunchangedActive-only candidacy; merge keeps the existing purchase date, refreshes receiptText.
  • Migration: lightweight (added property with a default — SwiftData migrates in place; adding #Index is also a lightweight change). One-time backfill at launch: fetch rows where normalizedName == "" and recompute from name. Idempotent, milliseconds, becomes a no-op.
  • No new entities. If the product/batch model is ever revisited, normalizedName is exactly the future product key — this schema is a strict subset of that one.
  • New Core files (all Linux-testable): NameKey.swift, ArtInference.swift, MergePlanner.swift, NameSearch.swift.

8Answers to #26's open questions

Open questionResolution
Matching key: name + storage enough, or should artKey/ItemID participate? Normalized name alone (owner call). Storage adds nothing — one name means one thing in a household, and a merge keeps the item where it lives. artKey is now derived from the name, so it carries no independent identity signal; its generic buckets would only block correct merges.
Should the review sheet surface impending merges? No (owner call — minimalism). The review page remains the explicit confirmation of what was scanned; the merge itself is silent and shows up as the grid staying truthful (×2 → ×3, no twin sprite). The badged variant was designed, animated (§4), and declined.
Skip merging when the existing item is near/past expiry? Skip only when expired (§5 rule 2). Near-expiry matches are usually the double-scan we want to group. The threshold lives in one pure function if it ever needs tuning.
Whole-receipt double-scan detection? Not now (owner call — no banners). If ever wanted: fingerprint the parsed (normalizedName, quantity) set, never the image (the expense-app pattern, §2). Purely additive later.
(settled in #26) Expiry conflict Preserved: the existing item's expiryDate/expirySource always win; a merge never overwrites them.

9Testing & build order

All decision logic is pure and Linux-testable in Tests/FridgeCoreTests/ (Gate: swift test):

  • NameKeyTests — folding ("Jalapeño"→"jalapeno"), trim/collapse, case rules beyond ASCII, empty/whitespace names.
  • ArtInferenceTests — exact hits, synonym hits, token fallback ("chocolate milk"→milk), multi-token head-noun choice, typo tolerance ("bannana"→banana; two edits ⇒ no match), unknown fallback, determinism (same input ⇒ same id). Tier-0 precedence (remembered art beats inference) is exercised where the history lookup lives, with a value-level test on the "latest row wins" grouping.
  • MergePlannerTests — match hit/miss, expired-candidate skip, multi-candidate tie → most recent purchase, quantity clamp at 99, within-receipt row coalescing.
  • NameSearchTests — tier ordering (exact > prefix > word-prefix > contains), diacritic-blind queries, recency/frequency tie-breaks, limit.

UI behavior (silent merge outcome, +1 suggestion, auto art, searchable filter) lands on the spec's acceptance-criteria checklist and is exercised on Appetize per the existing flow.

  1. Foundation — NameKey + normalizedName property + #Index + backfill + setName write discipline. Invisible, independently shippable.
  2. Merge at confirm — MergePlanner wired into ScanFlowModel.confirm and ManualAddSheet.add. Closes #26.
  3. Manual add, minimized — ArtInference replaces the ArtPicker; NameSearch drives the quick-fill chips row; merge-aware Add with the prefill-vs-edited expiry rule.
  4. Inventory lookup — .searchable on the home grid.

Steps 2–4 are separately reviewable PRs on the same foundation; none blocks another after step 1. On implementation, the owner calls recorded here (silent merge, name-only key, auto art, iOS 18 floor) go into wiki/decisions.md per repo convention.
